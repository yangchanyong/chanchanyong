Project V

AWS 기반 Spring 서비스의 Self-Hosted Re-platforming

2026.04 ~ 운영 중

AWS(EC2 + Aurora Serverless v2 MySQL + S3 + GitHub Actions)에서 운영하던 Spring Boot 서비스를 자체 서버 ARK(PostgreSQL 17 + S3 호환 Object Storage + Self-Managed GitLab CI/CD)로 옮겼습니다. 애플리케이션 코드(Spring Boot / Spring Data JPA, OAuth2 + JWT)는 유지하고, DB 엔진 · 스토리지 · 배포 경로 · 네트워크 경계를 새로 설계했습니다. 2026.09 Migration 완료 후 ARK에서 운영 중입니다.

Before · AWS (2026.04 ~ 08, Historical)

  • 컴퓨트 EC2 t3.micro + Docker + nginx
  • DB Aurora Serverless v2 (MySQL 8.0) + Flyway
  • 스토리지 S3 + Presigned URL + IAM 최소 권한
  • CI/CD GitHub Actions OIDC + production 수동 승인

After · ARK (2026.09 ~ 운영)

  • 컴퓨트 내부 Docker Network 컨테이너, 외부 직접 노출 없음
  • DB PostgreSQL 17 전용 DB/Role + PostgreSQL Flyway chain
  • 스토리지 S3 호환 Object Storage 서비스 전용 Bucket · 권한
  • CI/CD GitHub(원본) → GitLab(배포 사본) → Commit SHA Image → Health 확인 · 자동 Rollback
  • 판단: AWS 계정은 복구하지 않고 GitHub 소스 기준으로 재배포 — 운영 데이터·업로드 파일은 보존 가치가 없고 Secret은 재발급 가능해 유료 복구의 실익이 없었음
  • DB 전환: 스키마 변환(AUTO_INCREMENT → IDENTITY, DATETIME(6) → TIMESTAMP(6), TINYINT(1) → BOOLEAN), MySQL Flyway 이력은 보존하고 PostgreSQL chain을 분리 — 전환 시 테스트 52건 통과(현재 66건)
  • 스토리지: S3 SDK · Presigned URL 구조를 살리려 S3 호환 Object Storage 선택. exact Content-Length 서명, 동일 Key 재업로드 차단(412), HeadObject 재검증, Origin 제한 CORS, 10MiB 상한까지 운영 E2E
  • 운영 검증: Google / Kakao / Naver OAuth 로그인, Cloudflare → Nginx → Application HTTPS 경로, Actuator Health. 구 AWS DNS 레코드 잔존으로 TTFB 약 19.7초 → 레코드 삭제 후 정상화
